## Supported methods and overview <a id="access-service-api-v1-userwhitelist-check-supported-methods-and-overview" />

- `POST` - used to check which [Covata user](/2.16/admin/administering-users) accounts will be disabled by adding or deleting one or more [user whitelist rules](/2.16/admin/managing-user-whitelists).

## Detailed description <a id="access-service-api-v1-userwhitelist-check-detailed-description" />

This API endpoint checks which Covata user accounts will be disabled by [adding](/2.16/api/access-service-api-v1-userwhitelist) or deleting [one](/2.16/api/access-service-api-v1-userwhitelist-userwhitelistid) or [more](/2.16/api/access-service-api-v1-userwhitelist-bulk) user whitelist rules.

The user whitelist feature becomes enabled when at least one user whitelist rule has been added to/is specified on the Covata Platform.

An enabled user whitelist feature means that any user whitelist rules which are then either added to or deleted<sup>&#42;</sup> from the Covata Platform may result in several Covata user accounts being disabled.

Therefore, use this endpoint first to check which Covata user accounts will be disabled before adding or deleting any user whitelist rules.

<sup>&#42;</sup> Deleting the last user whitelist rule from the Covata Platform results in the user whitelist feature being disabled. When the user whitelist feature is disabled, be aware that:

- Covata user accounts *are not* [disabled](/2.16/api/access-service-api-v1-users-bulk) by *not having a user whitelist rule*.
- Directly [disabling or re-enabling Covata user accounts](/2.16/api/access-service-api-v1-users-userid-enable) has no impact on the user whitelist feature.
- Any [LDAP](/2.16/admin/administering-users#account-type) user accounts that were disabled by not matching/complying with a user whitelist rule (when the user whitelist feature was enabled) are automatically re-enabled when the Covata Platform next synchronizes with the LDAP server.
