## URL structure <a id="access-service-api-v1-keys-keyid-url-structure" />

```text
https://access-service.xy-company.com/api/v1/keys/{keyId}
```

where `{keyId}` is the ID of a cryptographic key.

## Supported methods and overview <a id="access-service-api-v1-keys-keyid-supported-methods-and-overview" />

- `DELETE` - used to delete a cryptographic key that has not been associated with a [Secure Object](/3.1/api/creating-secure-objects-and-collections#secure-object), which thereby frees up the unallocated key limit once this has been reached.

<Note>

This method takes no parameters.

</Note>

## Detailed description <a id="access-service-api-v1-keys-keyid-detailed-description" />

This API endpoint deletes an unallocated cryptographic key (i.e. a key which has not been associated with a Secure Object), which thereby frees up the default limit of 10 unallocated keys that can be generated per user's session/valid access token.

Unallocated keys typically result from failures in [associating a key with a Secure Object](/3.1/api/access-service-api-v1-objects) (i.e. initializing an *Incomplete* Secure Object).

## Supported roles and conditions <a id="access-service-api-keys-keyid-supported-roles-and-conditions" />

This API endpoint supports the following Covata user [roles](/3.1/admin/administering-users#a-users-roles) (as described in the [Covata Platform Administrator's Guide](/3.1/admin)) and conditions:

- [Originator](/3.1/admin/administering-users#originator-role), [Collaborator](/3.1/admin/administering-users#collaborator-role) and [Ad hoc](/3.1/admin/administering-users#adhoc-role) - a Covata user with any of these roles can call this endpoint on a [key they generated](/3.1/api/access-service-api-v1-keys).

The Covata Platform's resources available to one of these Covata users (above) is determined by the access token passed in the [header](/3.1/api/access-service-api-v1-keys-keyid#access-service-api-v1-keys-keyid-required-headers) of requests to this endpoint.

## Required headers <a id="access-service-api-v1-keys-keyid-required-headers" />

The appropriate access token as the `Bearer` token:

- `Authorization: Bearer a1b2c3d4-e5f6-g7h8-i9j0-k1l2m3n4o5p6`

## Returns <a id="access-service-api-v1-keys-keyid-returns" />

If the request succeeded, then an HTTP response status `200 OK` is returned.
