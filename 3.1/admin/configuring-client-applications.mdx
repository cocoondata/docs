title: "Configuring client applications"
---

Integrators can use the Covata Platform's API to develop their own applications that directly leverage Covata's powerful data-centric security features.

A Covata Platform administrator can configure the access that their integrators' applications have to their Covata Platform's resources, by 'registering' these applications on their Covata Platform instance. Access to these resources is based on the [OAuth 2.0 Authorization Framework](http://tools.ietf.org/html/rfc6749), which the Covata Platform uses for authentication and authorization.

From the Covata Platform's perspective, an integrator's application is a 'client application', regardless of whether this application is:

- A server-side web application,
- Designed to run natively on a mobile device such as a tablet or phone,
- Designed to run natively on any other operating system (e.g. destkop/laptop computers) or
- User agent-based (e.g. runs client-side in a web browser).

A client application cannot access any resources on the Covata Platform until it has first been [registered](/3.1/admin/configuring-client-applications#configuring-a-client-application) with the Covata Platform.

## Configuring a client application

The **Client Applications** page of Covata Administration (above) allows:

- The [registration of client applications](/3.1/admin/configuring-client-applications#registering-a-new-client-application) with the Covata Platform.
- Registered client applications on the Covata Platform to be [edited](/3.1/admin/configuring-client-applications#editing-a-registered-client-application) - for example, to modify a client application's permitted [grant types](/3.1/admin/configuring-client-applications#grant-types).
- Registered client applications to be [disabled or re-enabled](/3.1/admin/configuring-client-applications#disabling-or-re-enabling-a-client-application) - for example, to block a client application's access to the Covata Platform's resources (by 'disabling' that application).

### Registering a new client application

**To register a new client application with the Covata Platform:**

1. [Sign in](/3.1/admin/accessing-administration#signing-in) to Covata Administration.
2. Click the **Client Apps** option on the left of the [Covata Administration interface](/3.1/admin/accessing-administration#the-administration-interface) to open the **Client Applications** page.
3. Click the **Add New** button.
4. In the **Add Client Application** dialog box, complete the fields (described in detail the [table](/3.1/admin/configuring-client-applications#client-application-fields) below) to register the client application.
5. Click **Save** and the client application will appear as a new entry on the **Client Applications** page.

### Editing a registered client application

**To edit a registered client application on the Covata Platform:**

1. [Sign in](/3.1/admin/accessing-administration#signing-in) to Covata Administration.
2. Click the **Client Apps** option on the left of the [Covata Administration interface](/3.1/admin/accessing-administration#the-administration-interface) to open the **Client Applications** page.
3. Scroll to the relevant client application (if necessary) and click its **Edit** link.
4. In the **Edit Client Application** dialog box, modify the registered client application's fields, which are described in detail in the [table](/3.1/admin/configuring-client-applications#client-application-fields) (below).
5. Click **Save** and the registered client application will be updated.

In this specification, a 'client' refers to a client application and the 'authorization server' refers to the Covata Platform.  |

| Grant types | <a id="grant-types" />The [*authorization grant(s)*](http://tools.ietf.org/html/rfc6749#section-1.3) (also known as *grant type/s*) that the Covata Platform permits a client application to use to issue the application with an [*access token*](http://tools.ietf.org/html/rfc6749#section-1.4). <br />  An access token:  <br />•  Defines resources on the Covata Platform that are available to an authenticated Covata user (by virtue of their [roles](/3.1/admin/administering-users#a-users-roles)). A refresh token can initially be issued to a client application by the Covata Platform following successful OAuth 2.0 authentication and authorization. When the current access token expires, this refresh token is exchanged by the client application for a fresh access token from the Covata Platform (without the user having to re-authenticate). <br />The Covata Platform supports the following OAuth 2.0 [grant types**](/3.1/admin/configuring-client-applications#grant-type-explanation), listed in order from most secure down to least secure (along with the types of client applications best suited to implement these grant types):  <br />•  **Authorization Code** - Best suited for the following types of client applications:  <br />•  Server-side web applications. <br />•  Native desktop/laptop or mobile device applications. <br />For [more information](/3.1/admin/configuring-client-applications#authorization-code-characteristics) about this grant type, see the [Grant type details](/3.1/admin/configuring-client-applications#grant-type-details) table below. <br />•  **Implicit** - Best suited for user agent-based applications, such as one that runs client-side in a web browser. <br />        For [more information](/3.1/admin/configuring-client-applications#implicit-characteristics) about this grant type, see the [Grant type details](/3.1/admin/configuring-client-applications#grant-type-details) table below. <br />•  **Password** - Best suited for the following types of client applications:  <br />•  Native desktop/laptop or mobile device applications. <br />•  Administrator/system-run services (e.g. a scheduled job). <br />For [more information](/3.1/admin/configuring-client-applications#password-characteristics) about this grant type, see the [Grant type details](/3.1/admin/configuring-client-applications#grant-type-details) table below. <br /><a id="grant-type-explanation" /> ** In the context of Covata technologies, a *grant type* (or *authorization grant*) is a credential representing a Covata user's *authorization* to access that user's protected resources on the Covata Platform. This credential is used by the client application to obtain an access token. The following concepts are key components which are required to complete/obtain a grant type: <br />• *User credentials* - credentials that consist of a Covata user's [email](/3.1/admin/administering-users#email) address and password (which the Covata user either received in their original 'Covata account created' email notification or had changed themselves).<br />• *Client credentials* - credentials that consist of both the [client ID](/3.1/admin/configuring-client-applications#client-id) and [client secret](/3.1/admin/configuring-client-applications#client-secret).  |
| Access token validity | The number of seconds that an access token issued by the Covata Platform to a client application is valid for. Upon expiry of the access token, the client application would need to either:  <br />•  Issue a valid refresh token to the Covata Platform in exchange for a fresh access token, or <br />•  Request the Covata user to re-authenticate to the Covata Platform (with their user credentials) to obtain a fresh access token. <br />**Note:** To maximize security, it is recommended that access tokens have relatively short life spans (expiring within minutes up to only a few hours at most). |
| Refresh token validity | The number of seconds that a refresh token issued by the Covata Platform to a client application is valid for. This value must be greater than the access token validity value above. <br />  If a refresh token expires, the client application requires a Covata user to re-authenticate in order to continue accessing the Covata Platform's resources (which are available to that user). <br /> **Note:** This field is only used by the [authorization code](/3.1/admin/configuring-client-applications#authorization-code-characteristics) and [password](/3.1/admin/configuring-client-applications#password-characteristics) grant types (described in detail below). |
| Registered redirect URI(s) | A list of one or more valid Uniform Resource Identifiers (URIs) which the Covata Platform uses to verify the value of the [*redirect URI*](http://tools.ietf.org/html/rfc6749#section-3.1.2) (also known *redirection endpoint*) parameter sent by the client application to the Covata Platform (during an OAuth 2.0 authentication and authorization request to obtain an access token). If any part of the redirect URI sent by the client application (from the start of this URI) does not match one of the registered redirect URIs specified in this field, then the Covata Platform terminates the OAuth 2.0 authentication and authorization process. <br /> **Notes:**  <br />•  This field is only used by the [authorization code](/3.1/admin/configuring-client-applications#authorization-code-characteristics) and [implicit](/3.1/admin/configuring-client-applications#implicit-characteristics) grant types (described in detail below), since these grant types require users to authenticate directly through a web interface/user agent served by the Covata Platform. The client application's 'redirect URI/redirection endpoint' is what the Covata Platform redirects this user agent to after the authentication step. <br />•  If communication between the client application and Covata Platform occurs over the Internet and the client application's redirect URI (to which the Covata Platform sends its response containing the access token) is based on the HTTP protocol, then for security reasons, ensure that:  <br />•  This redirect URI has been configured to use HTTPS (not just HTTP). <br />•  The registered redirect URIs specified in this field are prefixed with `https://` - i.e. no URIs in this field should be prefixed by `http://`.  |

## Grant type details

The following table provides details about the OAuth 2.0 grant types that the Covata Platform can permit a client application to use (i.e. to issue that application with an access token). See [Grant types](/3.1/admin/configuring-client-applications#grant-types) (above) for an explanation about access tokens issued by the Covata Platform.

These details below explain the types of information conveyed between the client application and Covata Platform, as well as the mode by which this information is conveyed and hence, the security implications associated with implementing these grant types in a client application.

| Grant type | Details |
| --- | --- |
| Authorization Code | <a id="authorization-code-characteristics" />The authorization code [grant type](/3.1/admin/configuring-client-applications#grant-types) securely handles the conveyance of user credentials, client credentials and access/refresh tokens between the client application and Covata Platform. The Covata Platform authenticates both the user and client application with their respective credentials. User credentials are never exposed to the client application, since users authenticate directly through a web interface served by the Covata Platform. Furthermore, access/refresh tokens sent by the Covata Platform to the client application (after successful user authentication) can then be captured by the client application, reducing the ability of the Covata user to access the access/refresh tokens themselves. As such:  <br />•  This is the *most secure* (and hence, recommended) OAuth 2.0 grant type to implement in a client application. <br />•  The authorization code grant type should be implemented by client applications that are [server-side web applications](http://tools.ietf.org/html/rfc6749#section-2.1), since these types of applications can keep their source code (and hence, client credentials) private. Since the secrecy of client credentials can be maintained by the client application itself, these types of applications are known as 'confidential clients'. <br />•  This grant type can also be implemented by client applications that are '[native](http://tools.ietf.org/html/rfc6749#section-2.1)', such as mobile or desktop applications. However, it is assumed that client credentials are not secure in these types of applications and are capable of being extracted. Since the secrecy of client credentials cannot be maintained by the client application, these types of applications are known as 'public clients'. <br /> **Note:** *Relying on client credentials as a security measure in native applications is not recommended*, for the following reason:  <br />•  Since a native client application is a 'public client', if the application's client credentials are extracted and implemented in an unauthorized client application, then the Covata Platform is unable to verify the authenticity of the genuine client application based on these credentials. If the credentials of a Covata user (who accesses the genuine client application) were procured through some other means (e.g. phishing) and then utilized to authenticate to the Covata Platform through the unauthorized client application, then the unauthorized application could gain access to the Covata Platform's resources (which are available to that user). <br />If an integrator relies on client credentials for security in their native application (which is not recommended) and suspicion arises that these credentials have been stolen, then to immediately address this security breach, the integrator's client application would need to be [disabled](/3.1/admin/configuring-client-applications#disabling-or-re-enabling-a-client-application) to deny access to the Covata Platform of all unauthorized client applications (which have implemented these stolen client credentials). Unfortunately, this action denies access of all genuine client application installations too. Therefore, after re-configuring the registered client application with new client credentials (as well as rebuilding and rolling out a new version of the genuine client application containing these new client credentials), the client application can then be [re-enabled](/3.1/admin/configuring-client-applications#disabling-or-re-enabling-a-client-application) on the Covata Platform.  |
| Implicit | <a id="implicit-characteristics" />The implicit [grant type](/3.1/admin/configuring-client-applications#grant-types) securely handles the conveyance of user credentials between the client application and Covata Platform. The Covata Platform authenticates the user with their credentials. However, as part of the OAuth 2.0 protocol, the client application is not authenticated with this grant type; the Covata Platform only verifies the identity of the client application through the [client ID](/3.1/admin/configuring-client-applications#client-id). While a user's credentials are never exposed to the client application (because users authenticate directly through a web interface served by the Covata Platform); unlike the authorization code grant type, the access token is sent directly by the Covata Platform to the client application in a URI fragment. As such:  <br />•  This OAuth 2.0 grant type is a *less secure* to implement in a client application (than [authorization code](/3.1/admin/configuring-client-applications#authorization-code-characteristics) above) for the following reasons:  <br />•  Since the Covata Platform does not authenticate the client application, the Covata Platform cannot verify the authenticity of the client application. <br />•  The availability of the access token in the URI fragment sent by the Covata Platform can expose the access token to unauthorized parties for malicious use - including an attack via an authenticated Covata user (for example, by means of phishing). In such instances, the user's access/refresh tokens (i.e. sessions) can be [expired](/3.1/admin/administering-users#expiring-users-tokens-sessions). <br />•  As a result of this grant type's inherent risk in exposing access tokens to unauthorized parties, refresh tokens are not issued when using the implicit grant type. <br />•  The implicit grant type is typically implemented by client applications that are '[user agent-based](http://tools.ietf.org/html/rfc6749#section-2.1)', such as web browser applications where the executable code is downloaded and runs in the browser itself (rather than on a server), since the client credentials are available to the Covata user. The implementation of the implicit grant type in a web browser application can allow for the seamless integration of Covata user authentication and authorization with OAuth 2.0, whilst keeping the user credentials secure.  |
| Password | <a id="password-characteristics" />The password [grant type](/3.1/admin/configuring-client-applications#grant-types) delegates the handling of user credentials to the client application itself. Both the user and client credentials are sent from the client application to the Covata Platform for authentication. Access/refresh tokens sent by the Covata Platform to the client application (after successful user authentication) can then be captured by the client application, reducing the ability of the Covata user to access the access/refresh tokens themselves. Be aware that:  <br />•  This OAuth 2.0 grant type is *less secure* to implement in a client application (than both [authorization code](/3.1/admin/configuring-client-applications#authorization-code-characteristics) and [implicit](/3.1/admin/configuring-client-applications#implicit-characteristics) above), because the delegated handling of user credentials to the client application increases the possibility of these credentials being exposed to unauthorized parties for malicious use. Exposure of user credentials to the client application is minimized by the fact that these credentials need only be used once (for a single request by the client application) and exchanged for an access token; since this grant type can issue of refresh tokens (which is recommended) in exchange for fresh access tokens, there is no need for client applications to store user credentials. <br />•  The password grant type should only be implemented by [native](http://tools.ietf.org/html/rfc6749#section-2.1) client applications (i.e. mobile or desktop applications), when a high level of trust between the Covata user and the client application itself can be assured. These are client applications which:  <br />•  Are a part of the operating system they run on (i.e. client applications developed by the same organization/group who developed the operating system it runs on), <br />•  Execute with a high level of privilege, or <br />•  Were developed by Covata. <br />Assuming the client application meets this criterion of trust, the password grant type could also be implemented by such a client application when the more secure [authorization code](/3.1/admin/configuring-client-applications#authorization-code-characteristics) is neither available nor appropriate to implement.  |

## Disabling and re-enabling a client application <a id="disabling-or-re-enabling-a-client-application" />

Disabling a registered client application prevents any installations of the client application from accessing the Covata Platform. This is useful when a client application's access to the Covata Platform needs to be disabled (either temporarily or permanently), or suspicion arises that the client application's credentials have been stolen.

**To disable, enable or re-enable a registered client application on the Covata Platform:**

1. [Sign in](/3.1/admin/accessing-administration#signing-in) to Covata Administration.
2. Click the **Client Apps** option on the left of the [Covata Administration interface](/3.1/admin/accessing-administration#the-administration-interface) to open the **Client Applications** page.
3. To:

   - *Disable the client application* - click its green **Enabled** button (in the **State** column towards the right of the page), until this button changes red and indicates **Disabled**.
   - *Enable or re-enable the client application* - click its red **Disabled** button (in the **State** column) until the button changes green and indicates **Enabled**.

<Note>

When a client application is disabled it can still be edited. This feature allows a registered client application to be configured before access to the Covata Platform is enabled.

</Note>
