title: "Konfiguration von Client-Anwendungen"
---

Integratoren können anhand der API der Covata-Plattform ihre eigenen Anwendungen entwickeln, um die leistungsstarken, datenzentrierten Sicherheitsfunktionen von Covata direkt nutzen zu können.

Safe Share-Administratoren können den Zugriff solcher Anwendungen ihrer Integratoren auf die Ressourcen der Covata-Plattform konfigurieren, indem sie diese Anwendungen bei ihrer Covata-Plattform-Instanz „registrieren“. Der Zugriff auf diese Ressourcen stützt sich auf das [OAuth 2.0-Autorisierungs-Protokoll](http://tools.ietf.org/html/rfc6749), das die Covata-Plattform für die Authentifizierung und Autorisierung verwendet.

Aus der Perspektive der Covata-Plattform ist eine Anwendung eines Integrators eine Client-Anwendung, ungeachtet dessen, um welche der folgenden Arten von Anwendungen es sich handelt:

- eine serverseitige Webanwendung,
- eine als nativ für Mobilgeräte (z. B. Tablets oder Mobiltelefone) konzipierte Anwendung,
- eine als nativ für andere Betriebssysteme (z. B. Desktop- oder Laptop-Computer) konzipierte Anwendung oder
- eine Anwendung auf Basis eines Benutzer-Agenten (die z. B. auf Client-Seite in einem Webbrowser ausgeführt wird).

Client-Anwendungen können auf keine Ressourcen der Covata-Plattform zugreifen, solange sie nicht bei der Covata-Plattform [registriert sind](/3.3/de/admin-platform/configuring-client-applications#configuring-a-client-application).

## Konfiguration einer Client-Anwendung <a id="configuring-a-client-application" />

Über die Seite **Client-Anwendungen** der Safe Share-Verwaltung ([siehe oben](/3.3/de/admin-platform/configuring-client-applications#client-applications-page)) können die folgenden Maßnahmen ausgeführt werden:

- [Registrierung von Client-Anwendungen](/3.3/de/admin-platform/configuring-client-applications#registering-a-new-client-application) bei der Covata-Plattform
- Folgende Aktionen für auf der Covata-Plattform registrierte Client-Anwendungen:

  - [Bearbeitung](/3.3/de/admin-platform/configuring-client-applications#editing-a-registered-client-application), z. B. Änderung der zulässigen [Erteilungstypen](/3.3/de/admin-platform/configuring-client-applications#grant-types) einer Client-Anwendung, sowie
  - [Deaktivierung oder Reaktivierung](/3.3/de/admin-platform/configuring-client-applications#disabling-or-re-enabling-a-client-application), z. B. um den Zugriff einer Client-Anwendung auf Ressourcen der Covata-Plattform zu blockieren (indem die betreffende Anwendung „deaktiviert“ wird).

## Registrierung einer neuen Client-Anwendung <a id="registering-a-new-client-application" />

**Registrierung einer neuen Client-Anwendung bei der Covata-Plattform:**

1. [Melden Sie sich](/3.3/de/admin-platform/accessing-platform-administration#signing-in-to-platform-administration) bei der Safe Share-Verwaltung an.
2. Klicken Sie auf die Option **Client-Apps** links auf der [Oberfläche Safe Share-Verwaltung](/3.3/de/admin-platform/accessing-platform-administration#the-platform-administration-interface), um die Seite **Client-Anwendungen** aufzurufen.
3. Klicken Sie auf die Schaltfläche **Neue hinzufügen**.
4. Füllen Sie im Dialogfeld **Client-Anwendung hinzufügen** die (in der [Tabelle](/3.3/de/admin-platform/configuring-client-applications#client-application-fields) unten detailliert beschriebenen) Felder aus, um die Client-Anwendung zu registrieren.
5. Klicken Sie auf **Speichern**, und die neue Client-Anwendung erscheint als neue Eintragung auf der Seite **Client-Anwendungen**.

Sobald ein Zugriffs-Token abläuft, hat die Client-Anwendung keinen Zugriff auf die Ressourcen der Covata-Plattform mehr, bis der Benutzer sich bei der Covata-Plattform wieder authentifiziert oder ein [Aktualisierungs-Token](http://tools.ietf.org/html/rfc6749#section-1.5) verwendet wird, um einen neuen Zugriffs-Token zu erhalten. B. auf der Client-Seite in einem Webbrowser ausgeführt werden. <br />        Für [weitere Informationen](/3.3/de/admin-platform/configuring-client-applications#implicit-characteristics) über diesen Erteilungstyp siehe die Tabelle [Einzelheiten zum Erteilungstyp](/3.3/de/admin-platform/configuring-client-applications#grant-type-details) unten. <br />•  **Passwort** - am besten für die folgenden Client-Anwendungen geeignet:  <br />•  native Desktop-/Laptop-Anwendungen oder Anwendungen für Mobilgeräte <br />•  von Administratoren/Systemen ausgeführte Services (z. B. geplante Jobs). <br />Für [weitere Informationen](/3.3/de/admin-platform/configuring-client-applications#password-characteristics) über diesen Erteilungstyp siehe die Tabelle [Einzelheiten zum Erteilungstyp](/3.3/de/admin-platform/configuring-client-applications#grant-type-details) unten. <br />Das Dialogfeld **Client-Anwendung hinzufügen/bearbeiten** zeigt im Abschnitt **Erteilungstypen** auch die folgenden Optionen. Während diese Optionen selbst keine OAuth 2.0-Erteilungstypen sind, unterstützen sie die (oben genannten) OAuth 2.0-Erteilungstypen:  <br />•  **Aktualisierungs-Token zulassen** - legt fest, ob die Covata-Plattform der Client-Anwendung Aktualisierungs-Token ausstellen kann, mit denen die Client-Anwendung anschließend neue Zugriffs-Token anfordern kann. Dies ermöglicht es, die Sitzung eines Covata-Benutzers (potenziell unbegrenzt) fortzusetzen, ohne dass der Benutzer sich nach dem Ablauf seines Zugriffs-Token neu anmelden muss. Diese Option ist nur anwendbar wenn der Erteilungstyp **Autorisierungscode** und/oder **Passwort** (siehe oben) gewählt ist/sind. <br />•  **Geräteregistrierung zulassen** - legt fest, ob die (auf einem spezifischen Gerät, d. h. meistens auf einer mobilen Plattform wie iOS oder Android ausgeführte) Client-Anwendung einen spezifischen Covata-Benutzer mit einer Kennung authentifizieren kann. Diese Anmeldeinformation wird von der Client-Anwendung genutzt, um einen Zugriffs-Token zu erhalten. ### Einzelheiten zum Erteilungstyp

Die folgende Tabelle beinhaltet Einzelheiten zu den OAuth 2.0-Erteilungstypen, deren Nutzung die Covata-Plattform Client-Anwendungen gestatten kann (d. h. über die der Anwendung Zugriffs-Token ausgestellt werden). Für eine Erläuterung der von der Covata-Plattform ausgestellten Zugriffs-Token siehe [Erteilungstypen](/3.3/de/admin-platform/configuring-client-applications#grant-types) (oben).

Die Angaben unten erläutern die verschiedenen Informationen, die zwischen der Client-Anwendung und der Covata-Plattform ausgetauscht werden, den Modus, über den dieser Austausch stattfindet, und damit die Auswirkungen auf die Sicherheit einer Implementierung dieser Erteilungstypen in einer Client-Anwendung.

| Erteilungstyp | Details |
| --- | --- |
| Autorisierungscode | <a id="authorization-code-characteristics" />Der [Erteilungstyp](/3.3/de/admin-platform/configuring-client-applications#grant-types) Autorisierungscode handhabt die sichere Übermittlung der Anmeldeinformationen des Benutzers und Clients sowie der Zugriffs- und Aktualisierungs-Token zwischen der Client-Anwendung und der Covata-Plattform. Die Covata-Plattform authentifiziert sowohl den Benutzer als auch die Client-Anwendung mit ihren jeweiligen Anmeldeinformationen. Benutzer-Anmeldeinformationen werden nie an die Client-Anwendung übergeben, da sich Benutzer direkt über eine von der Covata-Plattform bereitgestellte Weboberfläche authentifizieren. Nach der erfolgreichen Benutzerauthentifizierung können Zugriffs-/Aktualisierungs-Token von der Covata-Plattform sicher an die Client-Anwendung übermittelt werden, ohne dass diese Token einem Browser (d. h. Benutzer-Agent) gegenüber offen gelegt werden. Es gilt daher Folgendes:  <br />•  Dies ist der *sicherste* (und daher empfohlene) OAuth 2.0-Erteilungstyp für die Implementierung in einer Client-Anwendung. <br />•  Der Erteilungstyp Autorisierungscode sollte in Client-Anwendungen implementiert werden, bei denen es sich um [serverseitige Webanwendungen](http://tools.ietf.org/html/rfc6749#section-2.1) handelt, da diese Anwendungen ihren Quellcode (und daher ihre Client-Anmeldeinformationen) vertraulich halten können. Da die Vertraulichkeit von Client-Anmeldeinformationen von der Client-Anwendung selbst gewährleistet werden kann, werden diese Anwendungen als „vertrauliche Clients“ bezeichnet. <br />•  Dieser Erteilungstyp kann auch in „[nativen](http://tools.ietf.org/html/rfc6749#section-2.1)" Client-Anwendungen implementiert werden, z. B. mobilen oder Desktop-Anwendungen. Es wird jedoch davon ausgegangen, dass Client-Anmeldeinformationen bei diesen Anwendungen nicht sicher sind, sondern extrahiert werden können. Da die Vertraulichkeit von Client-Anmeldeinformationen von der Client-Anwendung nicht selbst gewährleistet werden kann, werden diese Anwendungen als „öffentliche Clients“ bezeichnet. <br /> **Hinweis:** *Es wird aus dem folgenden Grund nicht empfohlen, in nativen Anwendungen auf Client-Anmeldeinformationen als Sicherheitsmaßnahme zu vertrauen*:  <br />•  Da eine native Client-Anwendung ein „öffentlicher Client“ ist, kann die Covata-Plattform die Authentizität der echten Client-Anwendung anhand der Anmeldeinformationen nicht verifizieren, wenn die Client-Anmeldeinformationen der Anwendung extrahiert und in einer nicht autorisierten Client-Anwendung implementiert werden. Wenn die Anmeldeinformationen eines Covata-Benutzers (der auf die echte Client-Anwendung zugreift) auf anderen Wegen (z. B. Phishing) beschafft und dann verwendet werden, um sich über die nicht autorisierte Client-Anwendung bei der Covata-Plattform zu authentifizieren, könnte die nicht autorisierte Anwendung Zugriff auf die (dem betreffenden Benutzer verfügbaren) Ressourcen der Covata-Plattform erhalten. <br />Verlässt sich ein Integrator für die Sicherheit der nativen Anwendung auf Client-Anmeldeinformationen (was nicht empfohlen wird) und kommt der Verdacht auf, dass diese Anmeldeinformationen gestohlen wurden, müsste, um diese Sicherheitsverletzung unverzüglich zu beheben, die Client-Anwendung des Integrators [deaktiviert](/3.3/de/admin-platform/configuring-client-applications#disabling-or-re-enabling-a-client-application) werden, um alle nicht autorisierten Client-Anwendungen (in denen diese gestohlenen Client-Anmeldeinformationen implementiert sind) am Zugriff auf die Covata-Plattform zu hindern. Leider sperrt diese Maßnahme auch den Zugriff aller echten Installationen von Client-Anwendungen. Die Client-Anwendung kann daher nach einer Rekonfiguration der registrierten Client-Anwendung mit neuen Client-Anmeldeinformationen (sowie nach einem Rebuild und Roll-out einer neuen Version der echten Client-Anwendung mit den neuen Client-Anmeldeinformationen) auf der Covata-Plattform [reaktiviert](/3.3/de/admin-platform/configuring-client-applications#disabling-or-re-enabling-a-client-application) werden.  |
| Implizit | <a id="implicit-characteristics" />Der implizite [Erteilungstyp](/3.3/de/admin-platform/configuring-client-applications#grant-types) handhabt die sichere Übermittlung der Anmeldeinformationen des Benutzers zwischen der Client-Anwendung und der Covata-Plattform. Die Covata-Plattform authentifiziert den Benutzer mit seinen Anmeldeinformationen. Als Teil des OAuth 2.0-Protokolls wird die Client-Anwendung jedoch bei diesem Erteilungstyp nicht authentifiziert; die Covata-Plattform verifiziert lediglich die Identität der Client-Anwendung anhand der [Client-ID](/3.3/de/admin-platform/configuring-client-applications#client-id). Während die Benutzer-Anmeldeinformationen nie an die Client-Anwendung übergeben werden, da sich Benutzer direkt über eine von der Covata-Plattform bereitgestellte Weboberfläche authentifizieren, wird der Zugriffs-Token (im Gegensatz zum Erteilungstyp Autorisierungscode) von der Covata-Plattform in einem URI-Fragment direkt an die Client-Anwendung übermittelt. Es gilt daher Folgendes:  <br />•  Dieser OAuth 2.0-Erteilungstyp ist bei der Implementierung in einer Client-Anwendung aus den folgenden Gründen *weniger sicher* (als der [Autorisierungscode](/3.3/de/admin-platform/configuring-client-applications#authorization-code-characteristics) oben):  <br />•  Da die Covata-Plattform die Client-Anwendung nicht authentifiziert, kann die Covata-Plattform die Authentizität der Client-Anwendung nicht verifizieren. <br />•  Da der Zugriffs-Token im von der Covata-Plattform übermittelten URI-Fragment verfügbar ist, kann der Zugriffs-Token unbefugten Parteien zur böswilligen Nutzung übergeben werden, u. a. für eine Attacke über einen authentifizierten Covata-Benutzer (z. B. durch Phishing). <br />•  Aufgrund des diesem Erteilungstyp inhärenten Risikos, dass Zugriffs-Token unbefugten Parteien übergeben werden können, werden bei Verwendung des impliziten Erteilungstyps keine Aktualisierungs-Token ausgestellt. <br />•  Der implizite Erteilungstyp wird im Allgemeinen von Client-Anwendungen implementiert, die „[auf Basis eines Benutzer-Agenten](http://tools.ietf.org/html/rfc6749#section-2.1) wie z. B. Webbrowser-Anwendungen ausgeführt werden, bei denen ausführbarer Code heruntergeladen und im Browser selbst ausgeführt wird (statt auf einem Server), da die Client-Anmeldeinformationen dem Covata-Benutzer zur Verfügung stehen. Die Implementierung des impliziten Erteilungstyps in einer Webbrowser-Anwendung kann die nahtlose Integration der Covata-Benutzer-Authentifizierung und Autorisierung über OAuth 2.0 bei gleichzeitiger Sicherung der Benutzer-Anmeldeinformationen ermöglichen.  |
| Passwort | <a id="password-characteristics" />Der [Erteilungstyp](/3.3/de/admin-platform/configuring-client-applications#grant-types) Passwort delegiert die Handhabung der Benutzer-Anmeldeinformationen an die Client-Anwendung selbst. Sowohl die Benutzer- als auch die Client-Anmeldeinformationen werden der Covata-Plattform von der Client-Anwendung zur Authentifizierung übermittelt. Von der Covata-Plattform (nach der erfolgreichen Authentifizierung des Benutzers) an die Client-Anwendung übermittelte Zugriffs-/Aktualisierungs-Token können dann von der Client-Anwendung eingesammelt werden. Dies schränkt die Fähigkeit des Covata-Benutzers ein, selbst auf Zugriffs-/Aktualisierungs-Token zuzugreifen. Beachten Sie hierbei Folgendes:  <br />•  Dieser OAuth 2.0-Erteilungstyp ist bei der Implementierung in einer Client-Anwendung *weniger sicher* (als der Erteilungstyp [Autorisierungscode](/3.3/de/admin-platform/configuring-client-applications#authorization-code-characteristics) und der [implizite](/3.3/de/admin-platform/configuring-client-applications#implicit-characteristics) Erteilungstyp oben), weil die delegierte Handhabung der Benutzer-Anmeldeinformationen in der Client-Anwendung das Risiko erhöht, dass diese Anmeldeinformationen unbefugten Parteien für eine etwaige böswillige Nutzung übergeben werden. Das Risiko einer Übergabe von Benutzer-Anmeldeinformationen an die Client-Anwendung wird durch die Tatsache minimiert, dass diese Anmeldeinformationen nur einmal (für nur eine Anfrage der Client-Anwendung) verwendet und gegen einen Zugriffs-Token eingetauscht werden müssen. Da dieser Erteilungstyp es Client-Anwendungen ermöglicht, Aktualisierungs-Token für neue Zugriffs-Token zu übermitteln (was empfohlen wird), brauchen die Client-Anwendungen keine Anmeldeinformationen von Benutzern zu speichern. <br />•  Der Erteilungstyp Passwort sollte nur von [nativen](http://tools.ietf.org/html/rfc6749#section-2.1) Client-Anwendungen implementiert werden (d. h. mobilen oder Desktop-Anwendungen), wo von hohem Vertrauen zwischen dem Covata-Benutzer und der Client-Anwendung selbst ausgegangen werden kann. Dies sind Client-Anwendungen, die:  <br />•  Teil des Betriebssystems bilden, auf dem sie ausgeführt werden (d. h. die von derselben Organisation oder Gruppe entwickelt wurden wie das Betriebssystem, auf dem sie ausgeführt werden), <br />•  mit einem hohen Level an Privilegien ausgeführt werden oder <br />•  von Covata entwickelt wurden. <br />Sofern die Client-Anwendung dieses Vertrauenskriterium erfüllt, könnte der Erteilungstyp Passwort auch in Client-Anwendungen implementiert werden, für die der sicherere Erteilungstyp [Autorisierungscode](/3.3/de/admin-platform/configuring-client-applications#authorization-code-characteristics) weder verfügbar noch geeignet ist.  |

## Bearbeitung einer registrierten Client-Anwendung <a id="editing-a-registered-client-application" />

**Bearbeitung auf der Covata-Plattform registrierter Client-Anwendungen:**

1. [Melden Sie sich](/3.3/de/admin-platform/accessing-platform-administration#signing-in-to-platform-administration) bei der Safe Share-Verwaltung an.
2. Klicken Sie auf die Option **Client-Apps** links auf der [Oberfläche Safe Share-Verwaltung](/3.3/de/admin-platform/accessing-platform-administration#the-platform-administration-interface), um die Seite **Client-Anwendungen** aufzurufen.
3. Blättern Sie zur gewünschten Client-Anwendung (falls erforderlich) und klicken Sie auf den Link **Bearbeiten**.
4. Ändern Sie im Dialogfeld **Client-Anwendung bearbeiten** die (in der [Tabelle](/3.3/de/admin-platform/configuring-client-applications#client-application-fields) oben detailliert beschriebenen) Felder für die registrierte Client-Anwendung.
5. Klicken Sie auf **Speichern**, und die registrierte Client-Anwendung wird aktualisiert.

## Deaktivierung und Reaktivierung einer Client-Anwendung <a id="disabling-or-re-enabling-a-client-application" />

Die Deaktivierung einer registrierten Client-Anwendung verhindert, dass jegliche Installationen der Client-Anwendung auf die Covata-Plattform zugreifen können. Dies ist hilfreich, wenn der Zugriff einer Client-Anwendung auf die Covata-Plattform (vorübergehend oder permanent) deaktiviert werden muss oder wenn Verdacht besteht, dass die Anmeldeinformationen der Client-Anwendung gestohlen wurden.

**Deaktivierung, Aktivierung und Reaktivierung auf der Covata-Plattform registrierter Client-Anwendungen:**

1. [Melden Sie sich](/3.3/de/admin-platform/accessing-platform-administration#signing-in-to-platform-administration) bei der Safe Share-Verwaltung an.
2. Klicken Sie auf die Option **Client-Apps** links auf der [Oberfläche Safe Share-Verwaltung](/3.3/de/admin-platform/accessing-platform-administration#the-platform-administration-interface), um die Seite **Client-Anwendungen** aufzurufen.
3. Gehen Sie anschließend wie folgt vor:

   - *Zur Deaktivierung der Client-Anwendung* - klicken Sie auf die grüne Schaltfläche **Aktiviert** (in der Spalte **Status** rechts), sodass diese Schaltfläche auf rot wechselt und als **Deaktiviert** angezeigt wird.
   - *Zur Aktivierung oder Reaktivierung der Client-Anwendung* - klicken Sie auf die rote Schaltfläche **Deaktiviert** (in der Spalte **Status** rechts), sodass die Schaltfläche auf grün wechselt und als **Aktiviert** angezeigt wird.

<Note>

Eine Client-Anwendung kann auch bearbeitet werden, wenn sie deaktiviert ist. Diese Funktion ermöglicht es, registrierte Client-Anwendungen zu konfigurieren, ehe ihr Zugriff auf die Covata-Plattform aktiviert wird.

</Note>
